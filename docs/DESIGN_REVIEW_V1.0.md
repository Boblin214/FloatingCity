# 游戏设计审查记录 V1.0

- 审查日期：2026-11-10
- 最近更新：2026-11-10
- 对应总纲：`docs/GAME_DESIGN.md` V1.2
- 文档性质：审查意见与待确认问题

> 本文件中的建议均不是既定游戏规则。任何会影响玩法的调整，都应先由项目负责人确认。

## 一、当前实现基线

根据当前工程检查结果：

- 引擎为 Cocos Creator 3.8.8。
- 当前只有 `assets/scenes/Boot.scene` 基线场景。
- 场景由 `Canvas`、正交 `Camera` 和基础 UI 组件构成，设计分辨率为 1280×720。
- 尚未发现游戏脚本、预制体、正式美术资源、数据表、网络客户端或服务器代码。
- 当前引擎配置启用了 2D、UI、TiledMap、Spine、DragonBones、2D 物理等模块。
- `3d`、`skeletal-animation`、3D 物理和 WebSocket 模块当前未启用。

结论：当前工程处于空工程基线阶段，不存在玩法代码与设计总纲的直接规则冲突；但技术能力配置仍停留在 2D 基线，与长期目标存在明显差距。

当前项目继续保持只做设计准备，不开始正式玩法开发。

## 二、需要优先确认的设计问题

### 1. 伏击规则的适用边界（已明确）

强制驻留规则目前只适用于已经明确讨论的伏击任务，不扩展到以下场景：

- 普通行军。
- 采集任务。
- 讨伐任务。
- 寻宝任务。
- 守城任务。
- 其他任务类型。
- 其他战斗场景。

其他任务或战斗是否允许撤退、召回、改道、取消或驻留，仍需分别确认。不得把伏击的强制驻留当成全局默认规则。

本项作为已确认的维护边界记录，不再是待确认问题。

### 2. 强制驻留期间的非支援操作

总纲已明确不能召回、改目的地或提前取消，并且伏击任务期间禁止其他队伍支援。仍需确认：

- 是否允许使用道具、加速、治疗及其他非支援操作。
- 倒计时是否因维护、掉线或服务器停机暂停。
- 任务开始时锁定的是地点，还是也锁定阵型、装备和马车。

这些问题会直接影响玩家预期和网络断线后的行为一致性。

### 3. “全军覆没”的后续状态

总纲已明确，所有将领生命值全部归零才判定为全军覆没；只要一名将领存活就不算全军覆没。伏击期间全军覆没后，任务立即结束。

仍需确认：普通士兵或其他非将领单位全部损失、但将领仍存活时，战斗和任务如何继续或结束。该问题与全军覆没判定不同，不得自行把将领存活状态解释成全军覆没。

建议在实现战斗系统时，将“全军覆没判定”“战斗是否继续”和“任务终止条件”分别建模，避免把三者混成一个状态。

### 4. 自动返回的责任主体

伏击结束后的返程是否需要玩家在线、是否会因断线而暂停、返程目标是否始终是出发地或所属浮空城，目前没有规定。

建议技术上将“任务结束并生成返程”定义为服务器事件，不依赖客户端在线状态。

断线、掉线重连、服务器维护或停机后的伏击任务计时方式继续保留为待确认事项。

### 5. 其他任务是否驻留

采集、讨伐、寻宝及其他任务是否驻留，需根据任务性质分别确认。

伏击任务采用强制驻留，不代表其他任务同样采用该规则。

另有已确定规则：

- 伏击任务期间禁止其他队伍支援。
- 守城防御期间允许其他队伍支援。
- 守城支援的具体操作方式仍待确认。

### 6. 中央朝廷价格浮动口径

“固定基础价格，允许上下浮动约 5%”仍缺少确定口径：

- 每名玩家独立浮动，还是全服统一浮动。
- 按商品、类别、区域还是时间周期浮动。
- 刷新时点、随机范围和价格保护机制。
- 买入价与卖出价是否分别浮动。

这既是玩法问题，也是防止套利和刷资源的经济安全边界。

### 7. 玩家拍卖与朝廷交易之间的关系

如果朝廷低价收购极品马车、玩家又能自由拍卖，可能出现稳定的套利路径。需要在规则层明确：

- 朝廷是否收购马车。
- 拍卖是否限定特定品质或等级。
- 交易税、上架费、成交费和价格上下限。
- 流拍、撤拍、竞价延时和异常交易处理。

拍卖系统还涉及资产冻结、幂等结算与审计，建议在经济规则明确后再实现。

### 8. 两支远征队的并发上限

每名玩家拥有两支独立远征队，但是否允许两队前往同一资源点、同一城池或同一伏击点尚未确定。

该决定影响资源抢占、战斗合流、城池攻城队列和地图实体占用规则。

### 9. 高级城池的“长期争夺”

高级城池不能沿用低级城池的直接占领机制，这是明确规则；但“长期”的判定方式尚未确定。

可选方向应在规则层确认，例如积分阶段、控制窗口、开放争夺期或联盟贡献，但这些仅属于候选方案，不能直接视为既定设计。

### 10. 共享地图中的出生与资源公平

随机出生、各自初始探索区域和全服资源竞争可能造成以下问题：

- 出生区域资源品质不均。
- 相邻玩家数量差异导致早期强度差距。
- 玩家通过固定路线快速挤压其他出生区。
- 新玩家进入已高度开发的老服。

需确认是否需要出生保护、资源补偿、分线或赛季重置，但当前均未定案。

### 11. 迷雾探索进度是否永久保留

当前已明确需要独立探索进度、当前可见范围和服务器可见性过滤，但“已经探索过的区域是否永久保留迷雾探索进度”仍待确认。

该决定会影响玩家离线情报、赛季重置、地图缓存过期和探索收益，暂不自行确定。

## 三、未来技术架构重点

后续技术设计应优先关注共享大地图、服务器权威和任务状态持久化。以下内容为技术审查建议，不改变游戏规则。

### 1. 共享大地图与服务器权威

共享地图、伏击倒计时、战斗结果、资源结算和拍卖都涉及多名玩家，客户端时间与本地状态不可作为最终依据。

建议长期采用服务器权威模型：

- 服务器保存行军、任务、倒计时、战损和返程状态。
- 客户端负责输入、表现和短期预测。
- 关键结算使用服务器时间与幂等事件。
- 客户端重连后从服务器状态快照恢复，不依赖本地计时器“补算”结果。

#### 1.1 三种地图加载方案比较

| 方案 | 主要做法 | 优点 | 缺点与风险 | 未来扩展性 |
| --- | --- | --- | --- | --- |
| A. 只加载玩家自己的区域 | 客户端仅请求并加载玩家附近或所属区域 | 初期实现简单；本地内存、缓存和网络成本最低 | 无法形成公共连续地表；玩家难以发现他人、争夺资源和城池；跨区域移动体验不连续，不符合项目目标 | 低。后续加入共享探索时通常需要重做加载模型 |
| B. 加载玩家周围一定范围 | 根据玩家位置加载周围区块，并动态请求可见实体 | 能满足视野内探索；相比 A 支持公共地图和玩家相遇；按需加载降低一次性成本 | 静态资源也依赖临近时获取，快速移动或网络较差时容易加载延迟、空区块和画面跳变；重复下载可能增加流量 | 中等。可通过缓存逐步改善，但需要额外设计预取、缓存和卸载 |
| C. 静态资源预下载缓存，动态加载附近区块及服务器授权实体 | 地形和基础美术资源按版本缓存；客户端只加载附近区块；动态实体由服务器按可见性下发 | 同时满足公共大地图与按需渲染；降低重复下载和加载延迟；静态与动态数据解耦，便于性能优化和权限控制 | 需要本地缓存管理、资源版本更新、空间预算、区块卸载和较清晰的静态/动态数据边界；初期设计复杂度最高 | 最高。适合地图与玩家规模扩大，也便于以后调整区块、预取和服务器分区 |

审查建议：**方案 C 更符合当前设计方向，建议作为后续技术方案的首选方向。** 原因是它同时支持公共连续世界、附近动态加载、资源缓存和服务器可见性过滤，扩展空间最大。当前尚不确认具体缓存容量、预取距离和区块尺寸，方案 C 也不代表服务器、数据库或协议已经选型。

#### 1.2 地图区块划分建议

当前不确认区块尺寸。后续评估时应避免把“渲染区块”“服务器逻辑分区”和“持久化分区”强制绑定为同一尺寸。

- 渲染区块应优先服务于视锥、批处理、LOD 和局部卸载。
- 服务器逻辑分区应优先服务于兴趣管理、实体更新频率和并发。
- 持久化分区应优先服务于查询、事务范围、迁移和故障恢复。
- 区块边缘需要处理跨区实体、任务和跨区战斗，避免单位位于边界时状态分裂。

推荐后续用小、中、大三档地图规模做压力测试，以实际玩家密度、实体密度和目标设备预算反推尺寸，而不是现在凭经验定死。

#### 1.3 本地预下载与动态加载

当前不确认具体预下载区块数或距离。建议区分以下范围：

- 当前可见范围：必须渲染和相关动态信息应更新的范围。
- 静态资源预取范围：根据行军速度、镜头移动速度和网络状况提前下载静态区块。
- 动态订阅范围：服务器需要向客户端推送可见或规则允许感知的实体范围。
- 资源保留范围：离开视野后暂时保留缓存，使用滞回策略避免在区块边界频繁加载和卸载。

客户端应设置内存与磁盘预算，并优先清理远离当前区域、低优先级、旧版本的缓存。弱网、快速行军和镜头缩放需要分别测试。具体阈值必须通过原型测量后决定。

建议静态区块资源使用版本清单和完整性校验；新版本资源完整可用后再切换，异常缓存可以被识别和安全重建。具体缓存格式、校验算法和下载协议暂不定案。

#### 1.4 多人同区块与实体持久化

同一区块可能同时存在多名玩家、多个部队、战斗、资源点和城池。服务器需要基于空间位置管理动态实体的归属与订阅，避免每名玩家都触发一套独立世界模拟。

推荐关注：

- 服务器维护区块内动态实体索引和参与者集合。
- 根据可见范围与规则生成不同玩家可见的数据视图。
- 关键战斗、资源变化和城池状态只由服务器结算一次，统一广播给有权限的观察者。
- 没有玩家观察时，不应立即丢弃世界状态；可按规则降低模拟频率或转为事件驱动。
- 静态可重建内容与需要持久化的动态状态要分开管理。

资源刷新、怪物刷新、遗迹恢复和城池空闲状态属于玩法规则，仍待确认，不能因技术实现需要自行补全。

#### 1.5 开阔视野、迷雾与反作弊

地图静态资源提前缓存会扩大客户端可接触的数据量。静态地形、美术资源、配置表和运行时实体状态必须分层处理：

- 客户端可以缓存地形美术、通用图标和区块基础资源。
- 服务器只下发玩家有权知悉的动态实体及其必要字段。
- 不在客户端直接下发全局敌人位置后再用 UI 遮挡。
- 服务端校验玩家位置、探索范围和请求合法性，限制客户端查询任意区域。
- 动态可见性与探索进度应使用服务器权威状态；是否永久保留探索进度仍待设计确认。

仅对数据加密或混淆不能替代服务器可见性过滤，因为客户端最终仍可能观察和解包收到的数据。

#### 1.6 扩大规模后的扩展路线

全服逻辑上共享同一个真实世界，不等于所有玩家必须由同一台服务器长时间承载。未来可在逻辑世界不变的前提下按空间分区或分片承载。

扩展时应优先保证：

- 世界坐标唯一且稳定。
- 区块和实体具有明确归属，可跨进程移交。
- 玩家跨区、部队跨区和战斗跨区时具有原子移交边界。
- 任务事件通过服务器时间推进，不依赖玩家在线。
- 存储与查询可按空间范围切分，避免全表扫描。
- 网关、地图空间服务、任务服务和持久化层之间保留清晰边界。

具体采用单服空间分区、地图进程、分区服务器还是其他拓扑，仍需根据在线人数、同屏实体、同步频率和运营规模决定。

### 2. 任务状态持久化

长时任务可能跨越离线、网络切换和服务异常，不能只保存在客户端内存或依赖客户端倒计时。

建议关注：

- 服务器保存任务开始时间、结束时间、当前阶段和关键配置版本。
- 任务状态变化通过唯一事件标识，防止重复结算。
- 重连后以服务器保存状态为准恢复表现。
- 明确服务器时间、停机恢复和补偿的处理方式，具体计时规则仍由项目负责人确认。

### 3. 将“状态机”和“地图坐标”分离

部队至少涉及以下独立状态：

- 待命。
- 行军去程。
- 任务执行。
- 强制驻留。
- 返程。
- 战斗结算。
- 全军覆没/任务终止。

建议先建立统一任务状态模型，再由不同任务配置决定是否允许召回、改道、取消和受影响撤退。这样既能保证伏击规则稳定，也避免未来把所有任务硬编码成同一行为。

### 4. 地图数据不能全部一次性加载

连续共享大地图、全服玩家与大量静态实体不适合作为单个场景或单个完整纹理加载。

建议采用分块地图：

- 地图逻辑使用统一世界坐标。
- 客户端按视口和缓冲区流式加载地图块、图标与迷雾。
- 服务器按空间分区分片管理实体和交互。
- 静态内容、动态实体和玩家可见状态分层存储。

具体分块尺寸和分区方案应在地图规模与同屏密度确定后再定。

### 5. 迷雾应区分“探索记录”和“当前视野”

迷雾通常至少包含两个概念：

- 永久探索记录：玩家曾看见的区域轮廓与静态信息。
- 实时视野：当前队伍周围可见的动态单位和活动。

如果只保存一张当前迷雾图，重连、多队伍分开行动和远端情报会出现状态冲突。建议在数据模型中预留双层迷雾，但具体揭示规则仍需设计确认。

### 6. 伪 3D 表现与当前 2D 工程配置

当前工程未启用 3D、骨骼动画和 3D 物理，已有场景也是纯 2D Canvas。伪 3D 不一定要求完整 3D 物理，但可能涉及：

- 3D 摄像机或透视投影。
- 2.5D 场景分层。
- 地形高度与遮挡。
- 3D 或骨骼动画角色。
- 大世界 LOD 与合批策略。

建议先做一场包含地图缩放、迷雾、单位行军和城池图标的视觉技术验证，再决定最终渲染方案。当前阶段不宜因“伪 3D”就盲目启用全部 3D 模块。

### 7. 配置数据必须版本化

英雄、马车、城池、资源、任务时长和交易价格未来都可能调整。建议将规则参数放入可版本化数据表，并区分：

- 当前配置版本。
- 局内实体引用的配置版本。
- 服务器与客户端配置兼容范围。

尤其对于长时任务和拍卖，必须避免配置热更新后同一实体被两套规则结算。

### 8. 可观测性和运营安全需要预留

长期 SLG 必然需要排查资源异常、战斗争议、拍卖纠纷和任务卡死。建议从服务器架构初期预留：

- 关键事件审计日志。
- 任务与战斗的唯一事件 ID。
- 资源变更流水。
- 玩家客服查询接口。
- 任务补偿与幂等重放能力。

## 四、建议的开发顺序

以下为技术建议，不改变任何游戏规则：

1. 先确认地图规模、同步频率、同屏单位规模与目标平台。
2. 使用方案 C 作为候选方向，完成最小静态区块缓存、附近动态加载、服务器可见性过滤的纵切验证。
3. 完成服务器权威的最小行军/任务纵切，包括断线恢复、离线推进和返程。
4. 完成区块边界处多人同区、跨区行军和实体持久化的压力测试。
5. 在经济系统实现前，确认朝廷浮动价、拍卖税费与异常交易规则。
6. 用可丢弃的技术原型验证伪 3D 表现与大世界性能，再确定正式美术管线。

## 五、审查结论

当前项目没有与总纲冲突的玩法实现，因为玩法代码尚未开始。伏击强制驻留仍只适用于伏击；全军覆没已经确定以所有将领生命值归零为判定，伏击期间禁止支援，守城防御允许支援。普通单位全灭但将领存活后的战斗状态、伏击期间非支援道具操作、断线计时、守城支援操作和迷雾进度保留仍待确认。

技术层面，方案 C 与当前设计方向最匹配，建议作为首选候选：静态地图资源可预下载缓存，客户端只动态加载附近区块，动态实体由服务器按可见范围授权。正式实现前仍需通过压力测试确定区块划分、预下载距离、动态范围、缓存预算和服务器分区。当前阶段保持设计准备，不启动正式玩法开发。
